# HTTP — Hypertext Transfer Protocol

## Overview

HTTP (Hypertext Transfer Protocol) is an application-layer protocol used for communication between clients and web servers.

A client, such as a browser or `curl`, sends an HTTP request to a server. The server processes the request and sends an HTTP response.

Basic communication:

```text
Client
   │
   │ HTTP Request
   ▼
Server
   │
   │ HTTP Response
   ▼
Client
```

For plain HTTP, the communication is not encrypted, which means HTTP traffic can be observed in plaintext by a network capture tool such as Wireshark.

---

# 1. HTTP Request

An HTTP request is sent by the client to request a resource or submit information to a server.

Example:

```http
GET / HTTP/1.1
Host: example.com
User-Agent: curl/8.21.0
Accept: */*
```

The request can be divided into:

```text
GET / HTTP/1.1
│   │    │
│   │    └── HTTP version
│   └─────── Requested path
└─────────── HTTP method
```

---

# 2. HTTP Methods

HTTP methods describe what the client wants to do.

## GET

`GET` is generally used to retrieve a resource.

Example:

```http
GET / HTTP/1.1
Host: example.com
```

This requests the resource at `/`.

Another example:

```http
GET /login HTTP/1.1
Host: example.com
```

This requests the `/login` resource.

---

## POST

`POST` is generally used to send or submit data to a server.

Example:

```http
POST /login HTTP/1.1
Host: example.com
Content-Type: application/x-www-form-urlencoded

username=alice&password=test123
```

The submitted data is contained in the request body.

`POST` is not limited to login requests. It can be used to submit forms, send API data, upload information, and perform other operations.

---

# 3. Request Path / URI

The path identifies the resource being requested.

Example:

```http
GET /login HTTP/1.1
```

Here:

```text
/login
```

is the requested path.

A request for:

```http
GET / HTTP/1.1
```

uses `/`, which commonly represents the root/homepage resource.

---

# 4. HTTP Version

Example:

```http
GET / HTTP/1.1
```

`HTTP/1.1` identifies the HTTP protocol version being used for the request.

It does not describe what resource is being requested.

The request method and path determine what is being requested:

```text
GET /login
```

while:

```text
HTTP/1.1
```

identifies the protocol version.

---

# 5. Host Header

Example:

```http
Host: example.com
```

The `Host` header identifies the hostname that the request is intended for.

A server or server infrastructure can host multiple websites, so the Host header helps identify the intended host.

Example:

```http
GET /login HTTP/1.1
Host: example.com
```

This can be interpreted as:

> Request `/login` from the host `example.com` using HTTP/1.1.

---

# 6. User-Agent Header

Example:

```http
User-Agent: curl/8.21.0
```

The `User-Agent` header identifies the client software that generated the request.

For example, a request generated by a browser may contain information identifying the browser, while our lab request used:

```text
curl/8.21.0
```

because `curl.exe` was used to generate the request.

---

# 7. Accept Header

Example:

```http
Accept: */*
```

The `Accept` header indicates what media types the client is willing to receive.

```text
*/*
```

means that the client is willing to accept any media type.

---

# 8. HTTP Request Body

Some HTTP requests contain a body.

For example:

```http
POST /login HTTP/1.1
Host: example.com
Content-Type: application/x-www-form-urlencoded

username=alice&password=test123
```

The section after the headers is the request body:

```text
username=alice&password=test123
```

GET requests generally do not use a request body for normal web requests, while POST requests commonly contain one.

---

# 9. HTTP Response

After receiving a request, the server sends an HTTP response.

Example:

```http
HTTP/1.1 200 OK
Content-Type: text/html

<html>
    ...
</html>
```

The first line is the HTTP status line.

```text
HTTP/1.1 200 OK
│        │   │
│        │   └── Status description
│        └────── Status code
└─────────────── HTTP version
```

---

# 10. HTTP Status Codes

HTTP status codes communicate the result of a request.

They are grouped into categories:

```text
2xx → Success
3xx → Redirection
4xx → Client/request-related error
5xx → Server-related error
```

Common status codes:

| Status Code                 | Meaning                                       |
| --------------------------- | --------------------------------------------- |
| `200 OK`                    | Request succeeded                             |
| `301`                       | Permanent redirect                            |
| `302`                       | Temporary redirect                            |
| `400 Bad Request`           | Server could not process the request          |
| `401 Unauthorized`          | Authentication is required or unsuccessful    |
| `403 Forbidden`             | Request understood, but access is not allowed |
| `404 Not Found`             | Requested resource was not found              |
| `500 Internal Server Error` | Server encountered an error                   |

### 401 vs 403

These are particularly important in web security.

```text
401
↓
Authentication is required or has failed

403
↓
The server understood the request,
but access is not permitted
```

An authenticated user can still receive `403` if their account does not have sufficient privileges.

---

# 11. Response Headers

HTTP responses contain headers that provide additional information about the response.

Example:

```http
HTTP/1.1 200 OK
Content-Type: text/html
Content-Length: 1250
```

---

## Content-Type

```text
Content-Type: text/html
```

This indicates the type of data contained in the response body.

In this example, the response contains HTML.

Other examples can include:

```text
application/json
text/plain
image/png
```

---

## Content-Length

```text
Content-Length: 1250
```

This indicates the size of the response body in **bytes**.

It does not necessarily mean 1250 characters because characters can require different numbers of bytes depending on encoding.

---

# 12. Transfer-Encoding

During the HTTP Wireshark lab, the response contained:

```text
Transfer-Encoding: chunked
```

This indicates that the response body is transferred using chunks rather than a single `Content-Length` value.

Wireshark displayed:

```text
HTTP chunked response
```

and showed the response data being reassembled from the chunks.

---

# 13. Connection Header

Example:

```http
Connection: keep-alive
```

This indicates that the connection can remain open for additional communication rather than immediately being closed after the response.

---

# 14. Cookies

Cookies allow a server and client to maintain information across requests.

A server can send a cookie using the `Set-Cookie` response header:

```http
HTTP/1.1 200 OK
Set-Cookie: session=abc123
```

The browser stores the cookie and can later send it back to the server:

```http
GET /dashboard HTTP/1.1
Host: example.com
Cookie: session=abc123
```

Cookies can be used for several purposes, including maintaining sessions.

---

# 15. Sessions

A common use of cookies is identifying an existing user session.

For example:

```http
Cookie: session=abc123
```

The server can use the session identifier to associate the request with an existing session.

Conceptually:

```text
Browser
   │
   │ Cookie: session=abc123
   ▼
Server
   │
   └── Identify associated session
```

Not every cookie represents a session. Cookies can also be used for preferences, tracking, and other purposes.

---

# 16. Access Control and Sessions

Sessions are important when testing authorization.

For example:

```http
GET /admin HTTP/1.1
Host: example.com
Cookie: session=abc123
```

If the server responds:

```http
HTTP/1.1 403 Forbidden
```

the session may be authenticated but not authorized to access the requested resource.

In an authorized testing environment, comparing requests made with different legitimate sessions can help determine whether authorization controls are correctly enforced.

---

# 17. HTTP Over TCP

HTTP/1.1 commonly operates over TCP.

A simplified connection can therefore look like:

```text
TCP Three-Way Handshake
        │
        ▼
HTTP Request
        │
        ▼
HTTP Response
        │
        ▼
TCP Connection Termination
```

During the HTTP Wireshark lab, this sequence was visible.

The capture showed:

```text
TCP SYN
TCP SYN, ACK
TCP ACK
        ↓
GET / HTTP/1.1
        ↓
HTTP/1.1 200 OK
        ↓
TCP connection termination
```

---

# 18. TCP Segmentation and HTTP

An HTTP response can be larger than a single TCP segment.

During the lab, Wireshark showed:

```text
[2 Reassembled TCP Segments]
```

The HTTP response was carried across multiple TCP segments.

Wireshark reassembled those segments and displayed the resulting HTTP data.

Conceptually:

```text
HTTP Response
      │
      ▼
TCP Segments
 ┌────┬────┬────┐
 │ #1 │ #2 │ #3 │
 └────┴────┴────┘
      │
      ▼
Wireshark reassembles
      │
      ▼
HTTP Response
```

---

# 19. HTTP vs HTTPS

HTTP traffic is not protected by TLS.

For example:

```http
GET / HTTP/1.1
Host: example.com
```

can be visible in plaintext in a network capture.

HTTPS is essentially:

```text
HTTP
 +
TLS
 =
HTTPS
```

TLS encrypts the HTTP communication.

Therefore, with HTTPS, Wireshark normally cannot simply display the HTTP request and response contents in plaintext.

Instead, it will generally show encrypted application data.

---

# 20. HTTP vs HTTPS Ports

Common default ports:

```text
HTTP
Port 80

HTTPS
Port 443
```

Example:

```text
http://example.com
        ↓
TCP port 80
```

while:

```text
https://example.com
        ↓
TCP port 443
        ↓
TLS
        ↓
Encrypted HTTP communication
```

---

# 21. Wireshark HTTP Analysis

HTTP traffic can be isolated in Wireshark using:

```text
http
```

A typical HTTP exchange may look like:

```text
Client → Server
GET / HTTP/1.1
Host: example.com

Server → Client
HTTP/1.1 200 OK
Content-Type: text/html

<html>
    ...
</html>
```

Because this lab used plain HTTP rather than HTTPS, the request and HTML response could be observed in plaintext.

        ↓

---

# 23. Key Takeaways

* HTTP is an application-layer protocol used for client-server communication.
* HTTP requests are sent by clients.
* HTTP responses are sent by servers.
* `GET` is generally used to retrieve resources.
* `POST` is generally used to submit data.
* `/` represents the root path in the requests observed in the lab.
* `HTTP/1.1` identifies the HTTP protocol version.
* The `Host` header identifies the intended hostname.
* The `User-Agent` header identifies the client software.
* `Accept` indicates media types the client is willing to receive.
* Request bodies can contain submitted data.
* HTTP responses contain status codes and response headers.
* `200 OK` indicates a successful request.
* `403 Forbidden` indicates that access is not permitted.
* `404 Not Found` indicates that the requested resource was not found.
* `Content-Type` identifies the type of response data.
* `Content-Length` represents the response body size in bytes when used.
* `Set-Cookie` is used by servers to set cookies.
* `Cookie` is used by clients to send stored cookies back to servers.
* HTTP commonly operates over TCP.
* TCP can segment HTTP data across multiple packets.
* Wireshark can reassemble TCP segments and display the HTTP data.
* HTTP is plaintext unless protected by another mechanism.
* HTTPS is HTTP protected by TLS.
* HTTP commonly uses port 80.
* HTTPS commonly uses port 443.

---

# Conclusion

HTTP defines how clients and servers exchange web requests and responses.

A typical web request involves a client sending an HTTP request containing a method, path, and headers. The server processes the request and returns an HTTP response containing a status code, headers, and potentially a response body.

The Wireshark lab demonstrated this process at the packet level. A TCP connection was established, an HTTP GET request was sent, and the server returned a `200 OK` response containing HTML that could be observed directly in plaintext.

This provides the foundation for understanding how tools such as Burp Suite can intercept, inspect, and modify HTTP requests and responses.
